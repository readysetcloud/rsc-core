Persistent agents · build tool

An agent with a job to do

The fourth agent type, and the one you build and run yourself. It wakes up when something concerns it, takes its time like a person, chases goals across runs, keeps its promises, and checks in without being asked.

This one’s a build tool, not a hosted service. The persistent agent is the fourth agent type and the only one rsc-core doesn’t run for you. You define the type with definePersistentAgent, then deploy its router and task handler in your own stack, against your own table. Its events go out under their own source (agency.<name>), so the shared task Lambda never grabs them. All of it comes from the Strands-free @readysetcloud/agent/agency subpath, which I pulled out of the AI managers in ai-fantasy-league.
Why

What makes an agent feel alive?

A task that runs when you ask is a function. The AI managers in my fantasy league feel like actual league members, and it comes down to six behaviors.

It wakes up for what concerns it

It doesn’t react to everything. Each event type gets a rule that names which agents care and what kind of work it calls for.

It paces itself like a person

A cooldown keeps it from being woken twice for the same work. A seeded, right-skewed delay keeps it from replying the instant something lands, because no human does that.

It keeps pursuing a goal

A typed agenda built from what your code actually observes, never from what the model says it did. A goal stays open until it’s really done.

It keeps its promises

“I’ll look into that” turns into a record with a real lifecycle. One task owns it at a time, and results settle it, not words.

It shows up on its own

A scheduled check-in a few times a day. And “nothing to do” is a perfectly good answer that doesn’t even need a model call.

It never changes its mind on a replay

Every random roll is seeded by the event and the agent. Redeliver the same event and you land on the same task id with the same delay.

Define one

definePersistentAgent

One definition per agent type. It says who an instance is, what wakes it up, what it does for each kind of task, and how to tell what it still needs.

reviewer.ts

Here’s a code-review agent. The handlers are yours and usually call runAgent. The definition takes care of identity, pacing, idempotency, and state so you don’t have to.

import { definePersistentAgent, humanDelay } from '@readysetcloud/agent/agency';
import { runAgent } from '@readysetcloud/agent';

export const reviewer = definePersistentAgent<Persona, Need, Intent>({
  name: 'reviewer',
  tableName: process.env.TABLE_NAME,

  // Who an instance is and how it paces itself. null: not one of ours.
  profile: async (agentId) => {
    const row = await loadReviewer(agentId);
    return row && { persona: row.persona, pacing: { cooldownMs: 15 * 60_000, responseDelay: row.responseDelay } };
  },

  // What wakes it.
  rules: {
    'Pull Request Opened': {
      kind: 'review',
      agents: ({ detail }) => detail.reviewers,
      delay: humanDelay('considered', { deadline: (d) => d.dueAt }),
      request: ({ detail }) => `Review pull request #${detail.pr} in ${detail.repo}.`,
      payload: ({ detail }) => ({ repo: detail.repo, pr: detail.pr }),
    },
  },
  checkIn: { agents: () => listReviewerIds() },        // 9:00, 14:00, 20:00 ET by default

  // What it does, by task kind.
  tasks: {
    review: async (ctx) => {
      const { output } = await runAgent({
        input: ctx.request,
        systemPrompt: [persona(ctx.persona), 'Your open goals:', ...ctx.agendaLines((g) => `review #${g.data.pr}`)].join('\n'),
        outputSchema: ReviewSchema,
      });
      if (output.followUpTest)                       // “I’ll look into that flaky test”
        await ctx.promise({ kind: 'investigate', counterpart: author, source: { channel, ref: commentId, visibility: 'shared' },
                            intent: { test: output.followUpTest }, expiresAt: inTwoDays, request: `Investigate ${output.followUpTest}.` });
      return output.summary;
    },
    investigate: async (ctx) => { /* owns ctx.commitment: start, then waiting or closed */ },
    check_in: async (ctx) => {
      const due = ctx.dueCommitments((c) => flakeSeenAgain(c.intent.test));
      for (const c of due.reconsider) await ctx.redispatch(c, 'reconsider', `Look at ${c.intent.test} again.`);
      return 'nothing else to do';
    },
  },

  // After every task: what does it still need? The agenda is reconciled from this read.
  observe: async (ctx) => ({ needs: (await openReviewRequests(ctx.agentId)).map((r) => ({ id: `review:${r.pr}`, kind: 'review', data: r })) }),
});

handleTask(detail)Your task Lambda. Checks the task belongs to this type and principal, claims it once, loads the agenda and commitments, runs the kind’s handler, reconciles the agenda from observe, records the result, and emits Agent Task Completed.

Safety

Guards for agents nobody is watching

These agents run while you sleep, so the guardrails are on by default. None of them needs infrastructure you aren’t already deploying.

GuardOptionWhat it does
RetriesisRetryable (default isRetryableError)A throttle, timeout, network reset, 429 or 5xx, or state-write contention is rethrown with the claim given back, so the task Lambda’s invocation fails and EventBridge delivers the task again. Anything else ends as FAILED. Pass () => false to never retry.
Pausepaused()The kill switch. While it returns true, route dispatches nothing and handleTask drops what arrives, unclaimed. Back it with a variable, parameter, or row you can flip without a deploy.
Task captaskCap (default 100 per agent per rolling day)Bounds runaway loops of check-ins, follow-ups, and promises. Each task id counts once, so retries are free. A capped task ends as FAILED with the reason; null turns it off.
A retried task runs its handler again, so make your handlers safe to repeat. Use ctx.taskId as the idempotency key for anything with side effects. Follow-ups and promises already have deterministic task ids, so they’re covered.
Deploy

Run it in your stack

Three small handlers, a table, and permission to put events on the bus. That’s the whole bill. Nothing gets deployed to rsc-core.

Handlers

Point each EventBridge rule at the agent’s own source.

// router.ts — rule: your app’s events, plus source "agency.reviewer" detail-type "Agent Check-In"
export const handler = (event) => reviewer.route(event);

// task.ts — rule: source "agency.reviewer", detail-type "Run Agent Task"
export const handler = (event) => reviewer.handleTask(event.detail);

// check-in.ts — schedule: cron(0 9,14,20 * * ? *), time zone America/New_York
export const handler = () => reviewer.emitCheckIn();
// Tests and local runs: everything in memory, no delays, tasks run inline.
import { definePersistentAgent, memoryAgentStore, memoryTriggerGates } from '@readysetcloud/agent/agency';

const reviewer = definePersistentAgent({
  ...definition,
  store: memoryAgentStore(),
  gates: memoryTriggerGates(),
  responseDelays: false,
  dispatch: async (task) => { await reviewer.handleTask({ taskId: task.taskId, principal: task.principal, request: task.request, trigger: task.trigger }); },
  onComplete: async () => {},
});

Shape

How the pieces fit

You can use any of these on its own. Put them together and you get the loop below.

  1. Route.Your event consumer calls routeTrigger with your rules. For each agent a rule concerns it takes the agent’s cooldown slot (a conditional write), computes a delay, and dispatches a Run Agent Task with a deterministic taskId and a trigger { kind, eventId, detailType, payload }. A delayed task is handed to Schedule Event named by its task id.
  2. Run.Your Run Agent Task consumer reads detail.trigger.kind to pick the task’s behavior, loads the agenda, puts agendaLines(...) in the prompt, and runs. Deterministic code decides what the agent may do. The agenda only decides what order to try things in.
  3. Reconcile.After acting, the task observes the real state again and reconcileAgendas it under updateAgentState. A goal completes only when the observation stops reporting the need. A pending request isn’t a result.
  4. Commit.When a conversation produces a promise, openCommitment records it by reference and the task dispatches a follow-up that owns it. The follow-up reports back through advanceCommitment, and a check-in picks up lost or reconsiderable ones.
  5. Check in.A cron emits an event carrying checkInMoment(now); a oncePer rule keyed by date and slot routes a check_in to every agent with a routine delay, so each one wanders in on its own time.
Triggers

Rules, gates, and delays

The router is a table of rules. Every rule answers four questions: who, what kind of task, how urgent, and how often.

Rule fieldMeaning
kindThe task kind requested; also the agent’s default cooldown slot, so a review never delays a reply.
agents(detail)Which agents the event concerns. Empty routes nowhere.
request(input), payload(input)The instruction the task runs and the ids it needs. Never the event’s untrusted text.
urgentBypasses cooldowns and delays (a deadline) but still starts the cooldown.
oncePer(detail)Fire once per key across every delivery and every event with that key (a daily window keyed by date).
cooldownA named slot and window instead of the agent’s baseline, shared by kinds that should pace together (every chat kind).
sharedCooldownOne reaction per moment across all agents the rule reaches.
admit(input)A per-agent gate before the cooldown: a personality roll, a budget check. Returns a reason or null.
delay(input)Milliseconds to wait. humanDelay(profile, { deadline }) builds the usual one.
GateSlotSemantics
Once-per keyrule#{kind}#{key}Taken once, forever (windowMs: null). A redelivery of the same event passes again because it is the owner.
Shared cooldownrule#{kind}#shared#{key}Last taken at least ms ago, or the owner’s.
Agent cooldown{agentId}#{kind or slot}As above with the agent’s baseline window; urgent sets the window to 0 and always passes.
Every gate is an owner-checked conditional write (dynamoTriggerGates in production, memoryTriggerGates in tests). Two deliveries racing for the same gate can’t both win. A retry of the same event passes its own gates again and lands on the same task id, where runAgentTask’s claim turns it into a no-op.

Response delays

Real people don’t answer in 200ms. The delay is a right-skewed sample sized by the kind of event, scaled by the agent’s temperament, capped, and squeezed to a share of whatever time is left before a deadline.

import { responseDelay, RESPONSE_DELAY_PROFILES } from '@readysetcloud/agent/agency';

// Profiles: prompt (seconds), conversational (minutes), considered (~45m, cap 8h), routine (~90m, cap 12h)
const { delayMs, reason } = responseDelay({
  profile: 'considered',
  seed: `${eventId}:${agentId}`,                      // same seed, same delay
  lever: { multiplier: 1, immediateChance: 0.1 },     // part of the persona; { 0, 1 } answers at once
  now,
  deadline: offer.expiresAt,                          // never past half the time left
});
Agenda

Goals that come from reality

A model’s summary of what it was doing is lossy, and it never knows when it’s finished. An agenda does.

RuleEffect
Observed, not claimedNeeds come from a fresh authoritative read the host performs. The model never completes a goal.
IdempotentThe same need reported again creates nothing. The same id in the same epoch keeps its createdAt.
Stable orderingA still-open goal keeps its place ahead of newly discovered needs, so the agent does not thrash between priorities.
Stale reads rejectedAn observation older than the last, or from an earlier epoch, changes nothing.
CompletionA need that stops being reported completes its goal. A new epoch expires the old epoch’s goals. closed cancels them all.
BoundedAGENDA_LIMITS: three active goals, twelve in history, or your own.

Reconcile after acting

Once the agent acts, read the real state, reconcile under the revision-checked store, and put the active goals in the next prompt.

import { readAgentState, updateAgentState, reconcileAgenda, agendaLines, emptyAgenda, type Agenda } from '@readysetcloud/agent/agency';

type Need = { repo: string; pr: number; reason: 'requested' | 'stale' };

// Before the run: into the prompt.
const agenda = (await readAgentState<Agenda<Need>>({ agentId, name: 'agenda' }))?.value ?? emptyAgenda<Need>();
const lines = agendaLines(agenda, (g) => `Review ${g.data.repo}#${g.data.pr} (${g.data.reason})`);

// After the run: observe, then reconcile.
const open = await listOpenReviewRequests(agentId);        // an authoritative read
await updateAgentState<Agenda<Need>>({
  agentId, name: 'agenda',
  update: (current) => reconcileAgenda(current ?? emptyAgenda<Need>(), {
    at: new Date().toISOString(), taskId,
    needs: open.map((r) => ({ id: `review:${r.repo}#${r.pr}`, kind: 'review', data: r })),
  }),
});
Do
const rank = agendaPriority(agenda, (g) => serves(option, g));
const pick = legalOptions.sort((a, b) => rank(b) - rank(a))[0];

Priority only orders options that already passed legality, budget, and permission checks.

Don't
if (agendaPriority(agenda, ...) > 0) overpay(option);

A goal is never a reason to overpay, skip a check, or step outside the agent’s authority.

Commitments

Promises with a lifecycle

What was asked, where, which task owes the work, what it decided and why, and whether anyone heard back.

TransitionWho may apply itEffect
openCommitmentThe task that heard the promiseIdempotent per source; duplicate for the same intent still open with that counterpart; limit when the agent already owes enough (three open, one per counterpart).
startThe assigned task onlyqueued → evaluating
waitingThe assigned task onlyRecords the external thing it produced (an offer id, a ticket) and waits on the counterpart.
closedThe assigned task onlyA final reason and the facts it rested on. reconsider: true schedules one more look after a cooldown, if the deadline allows.
settleA read of the system of recordWhat the counterpart did. Never from chat.
redispatchA check-inresume a queued look whose task never started; reconsider a due decline when materialChange finds something new. Bounded by child tasks and reconsiderations.

Record a promise, then dispatch the task that owns it

The text itself never gets stored. The follow-up re-reads the message by reference.

import { updateAgentState, openCommitment, emptyCommitments, taskIdFor, type CommitmentBook } from '@readysetcloud/agent/agency';

const followUpId = taskIdFor(`promise:${msg.id}`, agentId, 'investigate');
let outcome;
await updateAgentState<CommitmentBook<{ test: string }>>({
  agentId, name: 'commitments',
  update: (book) => {
    const r = openCommitment(book ?? emptyCommitments(), {
      kind: 'investigate', at: now, taskId: followUpId,
      counterpart: msg.from, source: { channel: msg.channel, ref: msg.id, visibility: 'shared' },
      intent: { test: 'flaky-login-spec' }, expiresAt: twoDaysFromNow,
    });
    outcome = r.outcome;
    return r.book;
  },
});
if (outcome === 'created') await dispatchFollowUp(followUpId, agentId);
// 'existing' (a redelivery) and 'duplicate' dispatch nothing; 'limit' means say so instead of promising.
Check-ins

The heartbeat

Fixed wall-clock times in the agent’s own time zone. If the job runs late or gets retried, it still counts as the same check-in.

Compute the moment, emit it, route it once

Out of the box that’s morning, afternoon, and evening, US Eastern.

import { checkInMoment } from '@readysetcloud/agent/agency';

// In the scheduled job (an EventBridge rule on a cron):
const moment = checkInMoment(new Date(), { timeZone: 'America/New_York', slots: { morning: 9, afternoon: 14, evening: 20 } });
await publish('Agent Check-In', { date: moment.date, slot: moment.slot, nextAt: moment.nextAt.toISOString() });

// In the rules:
'Agent Check-In': {
  kind: 'check_in',
  agents: () => listAgents(),
  oncePer: (d) => `${d.date}-${d.slot}`,
  delay: humanDelay('routine', { deadline: (d) => d.nextAt }),
  request: () => 'Look over your open goals and anything you said you would do.',
}
Under the hood

Using the primitives directly

This is the router definePersistentAgent builds for you, put together by hand. Reach for it when you need a different shape.

rules.ts

What wakes the agent and how it paces itself.

import { routeTrigger, humanDelay, dynamoTriggerGates, eventBridgeDispatcher, type TriggerRuleMap, type TriggerRouterDeps } from '@readysetcloud/agent/agency';

type PrOpened = { repo: string; pr: number; reviewers: string[]; dueAt: string };

const rules: TriggerRuleMap = {
  'Pull Request Opened': {
    kind: 'review',
    agents: ({ detail }: { detail: PrOpened }) => detail.reviewers,
    delay: humanDelay<PrOpened>('considered', { deadline: (d) => d.dueAt }),
    request: ({ detail }) => `Review pull request #${detail.pr} in ${detail.repo}.`,
    payload: ({ detail }) => ({ repo: detail.repo, pr: detail.pr }),
  },
  'Review Deadline Near': {
    kind: 'review',
    urgent: true,
    agents: ({ detail }: { detail: PrOpened }) => detail.reviewers,
    request: ({ detail }) => `Finish your review of #${detail.pr} now.`,
  },
};

const deps: TriggerRouterDeps = {
  rules,
  gates: dynamoTriggerGates({ prefix: 'reviewers' }),
  pacing: async (agentId) => {
    const persona = await getPersona(agentId);
    if (!persona) return null;                                 // not one of ours: skipped
    return { cooldownMs: 15 * 60_000, responseDelay: persona.responseDelay };
  },
  principal: (agentId) => ({ type: 'system', id: `reviewer/${agentId}` }),
  // Its own source, so the shared rsc-core task Lambda never runs these tasks.
  dispatch: eventBridgeDispatcher({ source: 'agency.reviewer' }),
  responseDelays: process.env.RESPONSE_DELAYS !== 'off',
};

export const handler = (event) => routeTrigger(deps, event);
DecisionMeaning
requestedDispatched (now, or scheduled by delayMs). Carries the taskId.
cooldownThe agent’s slot for this kind is still warm.
repeatThe once-per key was already taken by another event.
shared_cooldownAnother agent already reacted to this moment.
declinedThe rule’s admit turned the agent away; reason says why.
unknown_agentpacing() returned null: not an agent this router runs.
Boundaries

What it promises, and what it doesn’t (yet)

The guarantees, where each one comes from, and what I left out on purpose.

GuaranteeWhere it comes from
Observed, not claimedAgenda and commitment transitions take authoritative reads and task results; a model’s words never complete or settle anything.
Idempotent under at-least-once deliveryOwner-checked gates, deterministic task ids, idempotent openCommitment, stale-observation rejection, compare-and-swap state writes.
BoundedActive goals, open commitments per agent and per counterpart, history, child tasks, reconsiderations.
Private by constructionA commitment stores where something was said, never the text. Whether agenda lines reach a prompt that can post publicly is your call.
Yours to runNever hosted by the shared service: its events use their own source, and definePersistentAgent refuses the shared one.
Self-limitingRetryable failures are retried, a pause switch stops everything, and a per-agent task cap bounds loops.
Not here yet: the fantasy league’s durable dispatch outbox with its recovery sweep, and dollar-based budget admission. Both need extra infrastructure in your stack, and I didn’t want that to be the price of entry. For now, EventBridge retries a failed dispatch or a retryable task failure, and the task cap keeps spend in check. If you need dollar budgets, put them in your handlers.
