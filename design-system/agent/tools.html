Identity

Who the agent acts as

Identity is always the verified caller or a trusted first-party assertion, never a client value.

SurfaceIdentityVerified by
ChatThe Cognito sub in the bearer token on the socketAgentCore’s inbound JWT authorizer, against the shared user pool
POST /agent/sessions, /agent/connect, /agent/tasksThe Cognito sub of the API callerThe CoreApi Cognito authorizer
Run Agent Task eventThe principal in the event detailThe account-internal bus: only first-party Lambdas can put events on it
Session ownershipThe userId stored at creationThe host compares it to the verified caller at connect and at task time and refuses a mismatch
A leaked or guessed sessionId cannot resume someone else’s conversation, and memory is scoped by the verified id, so recall can never leak across users.
Principals

User tasks and system tasks

Two kinds of identity for autonomous work, with different trust.

{ type: "user", id: sub }

A verified person. Reuses session ownership and MCP identity propagation unchanged. The default for POST /agent/tasks.

{ type: "system", id: "booked" }

A service with no owning user, for ecosystem work. Asserting one is privileged: free for a first-party emitter on the internal bus, gated over the public API.

WhereGate
Internal bus (requestAgentTask)None: a first-party emitter is already trusted to assert a principal.
POST /agent/tasks { system }The SystemTaskPrincipals deploy parameter: comma-separated sub:systemId grants; sub:* allows any id; empty rejects all. Fails closed.
Launcher recordWhen a person launches a system task over the API, their sub is stored as createdBy so they can still read the task back even though the run acts as the system.

Granting a system principal

Opt in explicitly, like the MCP allowlist.

# sub abc-123 may run as "booked" only; svc-sub may run as any system id
SystemTaskPrincipals="abc-123:booked,svc-sub:*"
First-party tools

A registry a session selects from by name

Enabling a shipped tool per session is a data operation; authoring a new one is the only code change.

Register and select

The registry lives in the host. The package ships the type, the resolver, and two built-ins.

import { tool, builtinTools, resolveTools, createAssistant } from '@readysetcloud/agent';
import { z } from 'zod';

// Host registry: built-ins plus the host’s own.
const TOOL_REGISTRY = {
  ...builtinTools,                                   // http_request, notebook
  get_current_time: () => tool({
    name: 'get_current_time',
    description: 'Returns the current server time as an ISO-8601 string.',
    inputSchema: z.object({}),
    callback: async () => new Date().toISOString(),
  }),
};

// A session opts in by name: { tools: ['http_request', 'get_current_time'] }
const tools = resolveTools(config.tools, TOOL_REGISTRY, { sessionId, userId });
const agent = createAssistant({ sessionId, tools: [...tools, ...mcpClients] });
Built-inWhat it doesWatch out
http_requestGeneric HTTP client. The web-search seam: point it at a search API and let the model read the JSON back. Also any public REST endpoint or webhook.An outbound-request surface: the model chooses the URL. Front it with an allowlist or prefer a scoped MCP gateway when egress matters.
notebookAn in-invocation scratchpad the model writes to and re-reads across steps of a run.State lives in the invocation, not on the host.
Deliberately not exposed: the SDK’s bash and file_editor. In a shared hosted runtime, shell exec is remote code execution and filesystem access reaches the host’s disk. A host that wants them imports them from the SDK and registers them itself, as an explicit, auditable choice.
MCP servers

External tools, allowlisted and identity-aware

The one place a session points the runtime at an outbound URL.

Attach a server to a session

Keyed by label. The host connects them at build time and attaches their tools beside the first-party ones.

await createSession({
  userId,
  mcpServers: {
    blog: {
      url: 'https://mcp.example.com/mcp',
      headers: { 'x-api-version': '2025-01' },        // user-supplied; ${VAR} interpolated by the host
      authHeader: {                                     // authority-minted, forwarded verbatim
        name: 'x-booked-auth',
        value: '<base64url(payload)>.<sig>',
      },
    },
  },
});
ControlOwnerRule
SSRF allowlistHost (create-session)Rejects any mcpServers whose URL host is not in McpAllowedHosts. Empty rejects all, so it is opt-in.
SecretsHost environment${VAR} in string fields resolves against the host’s env. A secret never belongs in the session row, which the user creates.
authHeaderAn authority (a trusted server-side session creator)Mints a token binding tenant, user, session, and a version; the runtime forwards it verbatim, applied after user headers so they cannot shadow it, with no interpolation. The MCP server verifies it with the shared secret.
Threat model, stated plainly: the HMAC proves the authority minted this for user U; it does not prove the presenter is this runtime. That is acceptable because the config row is not user-reachable, the host is allowlisted, and transport is TLS. The token is replayed on every reconnect for the session’s ~30-day life, so bind it to the sessionId and include a version the authority can bump to revoke.
