Autonomous tasks

Do something, then report back

A one-shot run through the same secure path as chat, with no socket: triggered by an API call or an event, idempotent under duplicate delivery, and announced on the bus when it finishes.

Model

A task is a trigger, an identity, and a result sink

Chat needs a socket. A task needs those three things and nothing else.

Trigger

An API call (POST /agent/tasks) or a Run Agent Task event. Both land on the same consumer.

Identity

A Principal: { type: "user", id: sub } for a person, { type: "system", id: "booked" } for a service.

Result sink

One envelope, { taskId, status, output?, error? }, on the API response, the task row, and the Agent Task Completed event.

From a backend

Fire-and-forget. The owning stack’s consumer runs it and announces the result.

import { requestAgentTask } from '@readysetcloud/agent/memory';

const { taskId } = await requestAgentTask({
  principal: { type: 'system', id: 'booked' },      // or { type: 'user', id: sub }
  request: 'Summarize this week’s new blog comments',
  // optional: sessionId, systemPrompt, modelId, temperature, maxTokens, tools, mcpServers
});
// The event it emits (source "readysetcloud.agent", detail-type "Run Agent Task")
{
  "taskId": "6d1f...",
  "principal": { "type": "system", "id": "booked" },
  "request": "Summarize this week’s new blog comments",
  "trigger": { "kind": "digest", "eventId": "...", "detailType": "..." }   // present when a router sent it
}

From an app, waiting for the answer

The API records the task as PENDING, triggers the run, and polls its own row within the REST timeout.

curl -X POST "$CORE_API_URL/agent/tasks" \
  -H "Authorization: Bearer $ID_TOKEN" -H "Content-Type: application/json" \
  -d '{"request": "Draft release notes from the last 10 commits.", "wait": true}'

# 200 { "taskId": "...", "status": "COMPLETED", "output": "..." }
# or 202 { "taskId": "...", "status": "RUNNING" }  → watch "Agent Task Completed" or GET /agent/tasks/{taskId}
Lifecycle

Idempotent under at-least-once delivery

EventBridge may deliver twice. The task row makes that harmless.

  1. Warm cache.An in-memory TaskResultCache on the Lambda container answers a duplicate that lands on the same instance. An accelerator only; a miss is always correct.
  2. Durable claim.startTask is a conditional write that moves the row from absent, PENDING, or FAILED to RUNNING. DynamoDB serializes the writes, so exactly one of N deliveries wins. The losers return the existing result or report it in flight.
  3. Build after the claim.buildAgent runs only for the winner, so a duplicate never loads config or connects MCP servers.
  4. Run and record.One buffered turn (handleTask), then finishTask writes COMPLETED or FAILED, conditional on the row still being RUNNING.
  5. Emit.Agent Task Completed on every outcome, so async consumers are uniform whether or not a synchronous caller was still waiting.
StatusMeaning
PENDINGCreated by the API so a GET sees it before the runtime picks it up. Optional.
RUNNINGClaimed by exactly one invocation.
COMPLETEDFinished; output holds the assistant text.
FAILEDThe run threw; error holds the message. A retry may claim it again.

Running a task in your own host

The portable core has no runtime of its own. Any compute with the package installed can consume the event.

import { runAgentTask, createAssistant, getSessionConfig, TaskResultCache } from '@readysetcloud/agent';

const cache = new TaskResultCache();   // module scope — reused across warm invocations

export const handler = async ({ detail }) => {
  const { taskId, principal, request, sessionId } = detail;
  return runAgentTask({
    taskId, principal, request, sessionId, cache,
    buildAgent: async () => {
      const config = sessionId ? await getSessionConfig(sessionId) : null;
      if (config && config.userId !== principal.id) throw new Error('not your session');
      const agent = createAssistant({ sessionId: sessionId ?? `task-${taskId}`, systemPrompt: config?.systemPrompt });
      return { agent, cleanup: async () => { /* disconnect MCP clients */ } };
    },
  });
};
One-shot

runAgent: build, run, validate, forget

For orchestrators that call the model many times and want typed answers, not prose.

Structured output

Pass a Zod schema and the SDK forces the model to emit against it. A resolved call is a schema-valid one.

import { runAgent, tool } from '@readysetcloud/agent';
import { z } from 'zod';

const grammar = await runAgent({
  input: draft,
  modelId: 'us.anthropic.claude-lite-...',          // pin a model per lens
  systemPrompt: 'You are a grammar & spelling reviewer.',
  outputSchema: z.object({ suggestions: z.array(z.object({ span: z.string(), fix: z.string() })) }),
});
grammar.output.suggestions;                           // typed, validated

// A tool-using lens, with a bounded loop and trusted context the model cannot forge:
const searchBlog = tool({
  name: 'search_blog',
  description: "Search the tenant's own posts",
  inputSchema: z.object({ query: z.string() }),
  callback: async ({ query }, context) => searchWithinTenant(context?.invocationState.tenantId as string, query),
});
const facts = await runAgent({
  input: draft,
  systemPrompt: 'Fact-check claims using the blog search tool.',
  tools: [searchBlog],
  maxIterations: 6,
  invocationState: { tenantId, sub },                 // injected by trusted code, read by handlers
});
OptionEffect
outputSchemaZod schema; output becomes the validated object and structured is true.
toolsFirst-party tool()s, an McpClient, or a sub-agent.
maxIterationsCaps the tool loop (maps to the SDK’s per-invocation turn limit).
modelId, temperature, maxTokens, regionPer-call model selection.
invocationStateTrusted values threaded to every tool’s context.invocationState. Not a tool input, so the model never sees or sets it.
For a durable orchestrator, run the outer call as a task (runAgentTask) and let its lenses call runAgent. runAgent buffers the final answer; it does not stream.
